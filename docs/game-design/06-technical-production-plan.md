## 아키텍처와 엔진

엔진은 Godot 4, 2D 세로 화면이다. 계층은 사내 관례대로 넷으로 나눈다.

```text
domain/        규칙·판정·생성기·검증기. Godot 노드와 플랫폼 SDK 를 import 하지 않는다
application/   대국 조정, 기록 직렬화, 진행 저장, 리플레이 재생
infrastructure/ 원자적 파일 저장, 시계 주입, 원격 문서 포트, 광고·결제 포트
presentation/  화면, 위젯, 연출. command 생성과 state 렌더링만 한다
```

`domain` 이 순수한 것이 이 제품의 핵심 요구다. 리플레이 재생과 대국 진행이 **같은 판정 코드**를
쓰기 때문이다. 두 경로가 갈라지면 AC-005 가 깨진다.

물리 엔진을 쓰지 않는다. 군중은 개체 시뮬레이션이 아니라 정수 하나이고, 화면 표현만 그 수에
비례하는 인스턴싱이다. 따라서 군중이 500명이어도 판정 연산은 일정하다.

난수는 전부 `domain/rng/pcg32.gd` 의 PCG32 를 쓰고 **외부 시드를 해싱해 주입한다.**
Godot 의 `RandomNumberGenerator` 는 애벌랜치 효과가 없어 비슷한 시드가 비슷한 수열을 낼 수
있다고 공식 문서가 명시한다(SRC-006). 기록 재생은 수열이 영원히 같아야 성립하므로 엔진 구현에
기대지 않는 버전 고정 직접 구현을 쓰고, `RandomNumberGenerator` 는 규칙 경로에 쓰지 않는다(DEC-006). 생성기 상태에는 생성기가 낸 값 외의 임의 값을 넣지 않는다.

## 데이터 계약

원격에 저장하는 것은 사람당 문서 **1건**이다. 판마다 새 문서를 만들지 않고 같은 문서를 덮어쓴다.

```text
replays/{userId}
  schemaVersion: int        재생 규칙 버전
  displayName: string       표시명
  band: int                 대역 1~5
  courseSeed: string        해시 전 원본 시드
  picks: int[]              구간별 선택 인덱스 (0~2)
  commitExtended: bool      확약 시간 연장(DEC-008)을 켜고 둔 기록인지. 매칭 조건이며 판정과 무관
  createdAt: timestamp
```

**결과 수치를 저장하지 않는다.** 최종 군중 수와 승패는 재생 시 규칙이 다시 계산한다. 기록에
결과를 담으면 조작 경로가 생기고, 규칙 버전이 바뀌었을 때 원본과 재생이 어긋난다.

읽기는 대역과 확약 연장 여부가 같은 문서 1건을 가져오는 단일 쿼리다. 목록을 받아 클라이언트에서 고르지
않는다. 읽기 건수를 1건으로 묶기 위해서다(AC-006).

로컬 저장은 진행 대역, 승수, 깃털, 코스메틱 해금, 설정, 진행 중 판 상태다. 원자적 쓰기를 쓰고
손상 시 직전 정상 스냅샷으로 복구한다.

## 분석 이벤트 분류

질문 → KPI → 이벤트 → 파라미터 → 트리거 → 검증 순으로 설계했다. GA4 권장 게임 이벤트를
우선 재사용한다.

| 질문 | KPI | 이벤트 | 주요 파라미터 | 트리거 |
| --- | --- | --- | --- | --- |
| 온보딩을 넘는가 | 온보딩 완주율 | `tutorial_begin`, `tutorial_complete` | `segment_index` | 온보딩 시작·종료 |
| 반감 규칙이 전달되는가 | 2판째 선택 분포 변화 | `onboarding_split_seen`, `gate_commit` | `gate_type`, `is_split`, `duel_index` | 반감 발생, 확약 |
| 판을 끝내는가 | 판 완주율 | `level_start`, `level_end` | `band`, `segment_count`, `result` | 대국 시작·종료 |
| 하루 여러 번 여는가 | 세션당 판 수 | `duel_finish` | `session_duel_index` | 판 종료 |
| 상대 진위가 영향을 주는가 | 봇 판 포기율 | `opponent_resolved` | `opponent_kind`(record/bot) | 상대 확정 시 |
| 고정 전략이 생기는가 | 게이트 선택 분포 | `gate_commit` | `gate_type`, `my_crowd`, `opp_crowd` | 확약 |
| 광고가 성립하는가 | 옵트인율 | `rewarded_retry_optin`, `ad_reward_earned` | `placement` | 결과 화면 |
| 공유가 일어나는가 | 공유 탭율 | `result_share_tap` | `result` | 결과 화면 |

`gate_commit` 의 `my_crowd`, `opp_crowd` 파라미터가 있어야 불리기·모으기 전환점 근처에서
사람들이 실제로 무엇을 고르는지 볼 수 있다. 이것이 밸런스 회귀 검사의 입력이다.

## 성능 예산

| 항목 | 예산 | 측정 방법 |
| --- | --- | --- |
| 프레임 | 중급 기기 60fps 유지, 저사양 30fps 하한 | 대국 전 구간 프레임 로그 |
| 판정 1구간 | 1ms 미만 | domain 단위 벤치마크 |
| 코스 생성 + 검증 | 50ms 미만 | 생성기 벤치마크 |
| 군중 표현 | 500 개체에서 드로우콜 10 이하 | 인스턴싱, 200 초과 시 뒤쪽 실루엣 병합 |
| 앱 시작에서 첫 입력 | 3초 이내 | 콜드 스타트 계측 |
| 원격 읽기 지연 | 실패해도 판 시작을 막지 않음 | 500ms 초과 시 봇으로 전환 |
| 패키지 크기 | 80MB 이하 | 빌드 산출물 |

원격 읽기가 느리면 기다리지 않고 봇으로 전환한다. 대전 게임에서 대기 화면은 이탈 지점이기
때문이며, 이 정책이 성능 예산의 일부다.

## 저장 마이그레이션

로컬 저장과 원격 기록 모두 `schemaVersion` 을 가진다.

- 로컬: 버전이 낮으면 마이그레이션 함수를 순차 적용한다. 실패하면 진행을 초기화하지 않고
  읽기 전용으로 열어 사용자에게 알린다
- 원격 기록: **구 버전 기록은 그 버전의 규칙으로 재생한다.** 판정 규칙이 바뀌면 새 버전으로
  기록하고 재생 시 버전에 맞는 판정기를 고른다. 이 장치가 없으면 규칙 변경 순간 과거 기록이
  전부 어긋난다
- 규칙에 영향을 주는 값은 원격 설정으로 바꾸지 않는다(`05` 원격 설정 표)

## 백엔드와 보안 경계

- **상시 켜져 있어야 하는 서버가 없다.** Cloud Run 최소 인스턴스를 두지 않으며 전용 게임 서버가 없다
- 원격 연산은 문서 읽기 1건과 쓰기 1건뿐이다(AC-006)
- 보안 규칙: 자기 문서만 쓰고, 다른 사람 문서는 대역 조건으로 읽기만 가능하게 한다.
  `picks` 길이와 값 범위를 규칙 단에서 제한해 비정상 문서를 막는다
- 결과 수치를 기록에 담지 않으므로 결과 조작 경로가 없다. 조작하려면 선택 시퀀스를 바꿔야
  하는데, 그것은 그냥 다르게 플레이한 기록이 될 뿐이다
- 개인정보를 수집하지 않는다. 표시명은 사용자가 정하고 실명·연락처·위치를 요구하지 않는다
- 오프라인에서 전 기능이 동작한다. 원격은 상대 다양성을 높이는 보조 장치다

## 제작 단계

총 6주이며 각 주 끝에 확인 가능한 산출물이 있다.

| 주 | 목표 | 산출물 |
| --- | --- | --- |
| 1 | 규칙 코어 | `domain` 판정기, 게이트 4종, 반감·해소 순서. 헤드리스 테스트 통과 |
| 2 | 생성기와 검증기 | 코스 생성기, 4조건 검증기, 고정 전략 봇 6종. AC-002 / AC-004 달성 |
| 3 | 대국 화면 | SCR-002 플레이 가능. 확약 타이머, 동시 공개, 해소 연출 |
| 4 | 기록과 재생 | 선택 시퀀스 직렬화, 리플레이 재생, 봇 폴백. AC-003 / AC-005 / AC-007 달성 |
| 5 | 온보딩과 결과 | SCR-004, SCR-003, 결과 카드, 홈. AC-001 달성 |
| 6 | 다듬기와 QA | 피드백 채널, 접근성, 성능 예산, 기기 스모크 |

A-1 스타일 확정(`04` 승인 게이트)은 3주차 시작 전에 통과해야 한다.

## 빌드와 테스트 명령

사내 Godot 게임 저장소 관례를 따른다. 승인 전이므로 저장소를 만들지 않고, 승인 시점에 아래
진입점을 갖춘 구조로 승격한다.

| 목적 | 진입점 | 상태 |
| --- | --- | --- |
| 헤드리스 테스트 | `scripts/test.sh` — 도메인 테스트 전부. AC-003 과 AC-005 의 재현 검증을 포함한다 | 구현됨 |
| 생성기 대량 검증 | `scripts/validate_courses.sh --seeds 10000` — AC-002 | 구현됨 |
| 전략 승률 행렬 | `scripts/strategy_matrix.sh --courses 40` — AC-004 참고 지표 | 구현됨 |
| 정적 검사 | `scripts/lint.sh` — 임포트와 스크립트 컴파일. CI 게이트와 같은 범위 | 구현됨 |
| 디버그 빌드 | `scripts/build.sh --debug` — application ID 는 `com.seorilabs.crowdgateduel.debug` | 화면 구현 후 |

리플레이 재현은 별도 스크립트를 두지 않고 `test.sh` 안의 결정론 스위트가 담당한다.
같은 판정 코드가 대국과 재생 양쪽을 처리하므로 검증 경로를 나눌 이유가 없다.

Godot 헤드리스는 스크립트 오류가 있어도 종료 코드 0 을 낼 수 있다. 모든 진입점은
`scripts/_godot.sh` 를 통해 로그의 `SCRIPT ERROR` 와 `ERROR:` 를 함께 검사하고,
`timeout` 이 있는 환경에서는 명령 단위 타임아웃을 건다.

CI 는 main 에서 정적 검사와 헤드리스 테스트만 돌리는 사내 표준 게이트를 따르고, 마켓 업로드는
명시적 릴리스에서만 수행한다.
